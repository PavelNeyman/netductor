# Артефакты аудита и ревью — правила хранения в репозитории

## Назначение

Хранить code review, security audit, результаты тестов, проверки релизов, production-валидацию и инженерные решения в виде версионируемых и воспроизводимых файлов репозитория. Переписка в чате не является источником истины для проекта.

## Структура хранения

- `docs/audits/` — канонические отчёты аудитов и шаблоны на английском.
- `docs/ru/audits/` — русские версии с теми же находками, доказательствами, severity, статусами и рекомендациями.
- `docs/UPDATE-SYSTEM-IMPLEMENTATION-PLAN.md` и RU-пара — рабочий чек-лист реализации.
- Используйте дату, краткую область проверки и по возможности базовый commit в имени файла, например:
  - `docs/audits/2026-10-28-update-paths-bf54587.md`
  - `docs/ru/audits/2026-10-28-update-paths-bf54587.md`

Если отчёт слишком велик для одного файла, разделите его по подсистемам и добавьте индекс/обзор со ссылками на все части. Связанные EN/RU-пути должны быть параллельными.

## Обязательное содержание каждого аудита/отчёта

1. **Метаданные:** дата/время и часовой пояс, репозиторий, точный SHA базового commit, релиз/тег при необходимости, автор/инструменты при необходимости и область проверки.
2. **Вопрос и метод:** что проверялось, какие пути/файлы/команды изучались и какие области явно исключены.
3. **Окружение:** ОС/toolchain/зависимости для выполненных тестов; отдельно указывать статический просмотр исходников и реально запущенные тесты.
4. **Результаты:** сводка, подтверждённые находки, гипотезы, неизвестные и пункты, требующие проверки живого флота/оператора.
5. **Карточки находок:** стабильный ID, severity, затронутый компонент/путь, предусловия, влияние, доказательства, исправление, регрессионный тест, статус и ссылки на issue/PR.
6. **Верификация:** точные команды, exit status, число тестов/краткий вывод и то, что не запускалось. Нельзя заявлять об успешном тесте, если он фактически не запускался.
7. **Решение и продолжение:** принятые/отклонённые рекомендации с обоснованием, открытые риски, следующее действие, ответственный при известности и ссылки на план/задачи.
8. **Языковой паритет:** EN и RU-отчёты содержат одинаковые существенные находки и операционные детали. Обновляйте обе версии в одном изменении.

## Доказательства и защита секретов

- Не коммитить пароли, API/bearer/recovery-токены, приватные ключи, session cookies, seed-материал, полные production-конфигурации, UUID пользователей и другие рабочие учётные данные.
- Редактировать чувствительные имена хостов/IP и идентификаторы, если они не нужны для анализа. Последовательно использовать стабильные placeholders, например `PRIMARY_A`, `SECONDARY_B`, `<REDACTED_TOKEN>`.
- Предпочитать минимальный очищенный фрагмент с путём/строкой/commit полному выводу команды. Не прикладывать сырой `env`, secret stores, приватные ключи, неочищенные конфиги или неограниченные diagnostic bundles.
- Публичные и приватные ключи — разные вещи; всё равно проверяйте, можно ли связать публикуемый идентификатор или материал ключа с живым развёртыванием.
- Если чувствительные данные случайно закоммичены, недостаточно удалить их следующим коммитом: считать данные раскрытыми, уведомить оператора, при необходимости отозвать/ротировать их и следовать процедуре реагирования репозитория.

## Дисциплина прогресса и статусов

- Закрывать пункты плана только после выполнения критериев приёмки и добавления ссылки на отчёт/PR/доказательства теста.
- Использовать явные статусы: `confirmed`, `not reproduced`, `hypothesis`, `blocked`, `deferred`, `fixed — awaiting verification`.
- Изменение кода не доказывает, что дефект исправлен. Приложить регрессионный тест и записать его фактический результат.
- Статическое code review не доказывает поведение production. Проверки живого флота маркировать отдельно.
- Сохранять исторические отчёты неизменными по смыслу. Если последующие изменения кода делают находку неактуальной, добавить датированный follow-up или обновить статус со ссылкой на новые доказательства; не переписывать молча то, что было известно на момент аудита.

## Рекомендуемый процесс

1. Создать отчёт аудита по [шаблону](audits/TEMPLATE.md).
2. Перед проверкой зафиксировать точный базовый commit.
3. Собирать только необходимые очищенные доказательства.
4. Сверить каждую находку с исходниками и/или воспроизводимым тестом.
5. Сохранить EN/RU-пару отчётов в указанных каталогах.
6. Добавить ссылки на отчёт в соответствующий пункт плана, issue/PR и индекс документации.
7. После исправления приложить доказательства верификации и обновить статус находки; не закрывать план до прохождения критериев приёмки.
