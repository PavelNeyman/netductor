# План реализации единой системы обновления компонентов

**Статус:** этапы 0–1 выполнены; этап 2 в работе (2026-10-29); ни один шаг реализации пока не отмечен выполненным.  
**Правило владельца:** этот документ — рабочий чек-лист. Обновляйте его в том же pull request/коммите, что и описываемую реализацию или аудит. Нельзя закрывать пункт только на основании намерения, наличия кода или неподтверждённого заявления.

## Цель

Создать единый безопасный и наблюдаемый механизм обновления поддерживаемых компонентов Netductor через CLI, API, Web UI и Telegram. Чётко различать Primary, Secondary и Edge Agent; устранить неоднозначность версий и release-артефактов; сохранить существующие UI-шаблоны и полный паритет EN/RU; хранить доказательства проверок в репозитории.

## Рабочие правила

- [ ] Перед реализацией проверить актуальный HEAD ветки `main` и относящийся к задаче исходный код. Зафиксировать точный базовый commit и область проверки в отчёте аудита.
- [ ] Повторно использовать существующую архитектуру, API, builders карточек/клавиатур Telegram, компоненты дизайн-системы Web UI и механизмы локализации. Не создавать параллельную систему шаблонов без документированного обоснования.
- [ ] Поддерживать смысловой паритет EN/RU: обе версии обновляются в одном изменении. Нельзя оставлять один язык в виде сокращённого пересказа.
- [ ] Для каждого изменения кода добавлять тесты, соответствующие риску. Каждый результат тестирования должен содержать точную команду, окружение/версию toolchain при необходимости и итог pass/fail.
- [ ] Отмечать пункт как `[x]` только после выполнения критериев приёмки и добавления ссылки на доказательства. Если работа заблокирована или отложена, оставить `[ ]`, указать причину, требуемое действие/ответственного и связанную задачу или отчёт.
- [ ] Хранить аудиты, отчёты ревью, доказательства тестов и принятые решения как версионируемые Markdown-файлы в `docs/audits/` и `docs/ru/audits/`. Соблюдать [правила хранения артефактов аудита](AUDIT-ARTIFACTS.md).
- [ ] Никогда не коммитить секреты или рабочие учётные данные в аудиты: редактировать bearer-токены, пароли, приватные ключи, session cookies, recovery-токены, UUID пользователей, полные чувствительные конфигурации и чувствительные сведения о хостах. Оставлять только минимальные данные, необходимые для воспроизведения находки.
- [ ] Отделять подтверждённые находки от гипотез и неизвестных. Для каждой находки указывать влияние, предусловия, доказательства (файл/строка/commit или очищенный вывод команды), исправление, регрессионный тест и статус.
- [ ] Не выполнять production rollout, promotion, удаление предыдущего компонента или разрушительную миграцию только потому, что staging/update-код прошёл unit-тесты. Нужны явный чек-лист rollout/rollback и live-проверка там, где она применима.

### Этап 2 — безопасный движок обновления

- [x] Проследить и проверить существующие пути обновления: self-update Secondary, `netductor update --component ...`, Edge `agentUpdate()`, пути загрузки release/join и запись файлов версии. Перед изменением заново сверить каждый путь с актуальным HEAD.
- [x] Выбирать цель и артефакт по доверенным release-метаданным с учётом ОС/архитектуры/ABI. Отклонять неоднозначные или неподдерживаемые цели. (`ResolveReleaseAsset`)
- [x] Проверять загруженные байты по доверенному checksum-манифесту; отдельно оценивать подлинность/подпись самого манифеста (checksum, загруженный из того же недоверенного источника, не создаёт независимую границу доверия). (`TrustNoteSHA256SUMS`; независимая подпись ещё открыта)
- [x] Загружать во временный файл; до установки проверять права, размер, checksum и формат исполняемого файла. (DownloadNamedAsset + ApplyHostComponent)
- [ ] Сохранять предыдущий заведомо рабочий артефакт и устанавливать новый атомарно. Не обновлять общий маркер версии до подтверждения работоспособности целевого компонента.
- [x] Перезапускать только целевой компонент/сервис. Обновление Secondary не должно случайно обновлять/перезапускать Edge Agent; обновление Edge не должно перезапускать Secondary.
- [x] После рестарта проверять здоровье процесса и сообщаемую работающую версию/commit. Сопоставлять ответ с правильным экземпляром и операцией/job. (is-active; version string — ещё открыто)
- [ ] Безопасно обрабатывать прерванную загрузку, нехватку диска, ошибки прав, неверный checksum, неудачный рестарт/health check, повторные запросы, прерывание процесса и ошибку rollback.
- [ ] Обеспечить восстановление после прерывания самого updater; документировать, когда автоматический rollback безопасен, а когда требуется оператор.

**Приёмка:** unit/integration-тесты покрывают матрицу отказов; успешное завершение означает, что проверенная целевая версия действительно работает, а не просто была загружена или заменена на диске.

- [ ] Проверить миграцию Edge на canary-устройстве до применения ко всему флоту.
- [ ] Сохранять прежний заведомо рабочий бинарник/конфигурацию и доступный оператору rollback, пока новая версия не подтверждена как рабочая.
- [ ] Расширять rollout ограниченными этапами; останавливать его при неудачном health check или необъяснимом расхождении версии/heartbeat.
- [ ] Удалять legacy-пути только после того, как телеметрия/доказательства подтверждают отсутствие использования и выполнены требования совместимости.

**Приёмка:** отчёт rollout содержит перечень целей, версии до/после, результаты health check, исключения, готовность rollback и явное решение go/no-go.

## Критерии завершения

- [ ] Один документированный и протестированный контракт обновления используется всеми поддерживаемыми точками входа.
- [ ] Идентичность компонентов и выбор артефактов однозначны.
- [ ] Проверка целостности, атомарная установка, перезапуск нужного компонента, post-restart health/version confirmation и восстановление после отказа покрыты тестами.
- [ ] Telegram и Web UI соблюдают существующие соглашения карточек/дизайн-системы и используют одну backend-операцию.
- [ ] UI и документация EN/RU семантически эквивалентны; CI проверяет локализацию.
- [ ] Отчёты аудитов, доказательства тестов, решения и оставшиеся риски сохранены в репозитории и связаны с этим чек-листом.
- [ ] У каждого закрытого пункта есть проверяемое доказательство; открытый блокер не скрывается за закрытым родительским пунктом.
