# Срочный переход на второй Secondary и целевая HA-архитектура

**Статус:** план принят к исполнению  
**Приоритет P0:** развернуть второй Secondary и перевести на него рабочий трафик до отключения текущего сервера (ориентир — несколько дней).  
**Приоритет P1:** устранить архитектурную зависимость платформы от одного Primary и перейти к региональной модели RU/INTL.

Документ разделяет срочную миграцию и целевую архитектуру. Срочная миграция выполняется на существующей модели Netductor, но не должна закреплять её как долгосрочную.

## 1. Принятые решения

1. Второй Secondary **нужно развернуть сейчас**. Откладывать его до завершения проектирования новой HA-схемы нельзя.
2. Текущий Secondary/узел, который скоро отключат, остаётся рабочим до завершения переключения и окна наблюдения. Не удалять его заранее.
3. Новый Secondary разворачивается как отдельный peer с собственным идентификатором, материалом, Reality-параметрами и сетевым слотом. Нельзя повторно использовать или принудительно заменять material действующего peer.
4. Переключение выполняется blue-green способом: deploy без promote → инфраструктурная проверка → реальный клиентский трафик по IP нового узла → ready/promote → обновление DNS/профилей при необходимости → окно наблюдения → только затем вывод старого узла.
5. Не считать успешный deploy, heartbeat или ping доказательством работоспособности VLESS для реального клиента.
6. Целевая архитектура — гибридная: самостоятельная работа регионов RU и INTL, межрегиональный резерв критичных сервисов; дополнительные сервисы могут оставаться региональными.
7. До реализации целевой схемы не переименовывать сущности и не менять публичные API без миграционного слоя и обратной совместимости.

## 2. P0 — срочный второй Secondary

### P0.1. Зафиксировать исходное состояние

- Получить актуальный inventory: Primary, текущие Secondary, их AgentID/PeerID, IP, роли, слоты, версии, публичные hostname и DNS.
- Снять backup конфигураций, material, пользовательских данных и состояния подписок. Секреты хранить только в защищённом виде; не помещать их в Git, логи или отчёт.
- Зафиксировать текущие значения DNS и способы возврата на старый узел.
- Проверить, что текущий узел продолжает обслуживать трафик и доступен для rollback.
- Уточнить точное время отключения старого сервера и оставить запас на проверку и rollback.

**Выход:** согласованный inventory, проверенный backup и записанный rollback-путь.

### P0.2. Preflight нового сервера

- Проверить ОС/архитектуру, kernel, IPv4/IPv6, доступность SSH, firewall/UFW, свободные порты и отсутствие конфликтующих WireGuard-интерфейсов/подсетей.
- Проверить, что новый сервер не является тем же host/IP, что и существующий peer.
- Проверить актуальную версию Netductor и совместимость формата bootstrap bundle.
- Проверить SSH host key fingerprint по независимому каналу. При mismatch не сбрасывать trust автоматически.
- Проверить сетевую связность нового узла с Primary по требуемым портам.
- Не запускать параллельно несколько deploy-операций из одного operator-процесса, если они используют общий SSH port/config state.

**Выход:** сервер допускается к bootstrap без изменения текущего рабочего узла.

### P0.3. Deploy в режиме без переключения

- Зарегистрировать новый Secondary под новым AgentID и новым PeerID.
- Выделить свободный service-plane slot и уникальные WG-адреса/ключи.
- Выполнить provision и bootstrap штатным CLI-путём.
- Оставить promote выключенным.
- Проверить units, firewall, WG/WSS, локальные конфиги, права на файлы, свежий heartbeat и состояние агента.
- Проверить, что новый узел не изменил material, peer-конфигурацию, firewall или runtime-состояние старого узла.

**Выход:** новый узел установлен параллельно, старый продолжает обслуживать пользователей.

### P0.4. Проверка реального трафика

Проверить отдельно:

- VLESS listener и Reality-параметры нового узла;
- внешний TCP-доступ к публичному IP и порту;
- подключение реального тестового клиента с новым профилем;
- передачу данных в обе стороны и устойчивость соединения;
- выдачу подписки: в ней присутствует новый профиль с корректными pbk, sid, sni, адресом и уникальным идентификатором;
- работу критичных сервисов, которые должны быть доступны через новый узел;
- логи на предмет ошибок авторизации, TLS/Reality, routing, DNS и upstream.

Проверка должна выполняться с клиентской сети, не только с Primary или самого Secondary.

**Выход:** подтверждённый пользовательский трафик через новый узел.

### P0.5. Переключение и наблюдение

- Выполнить validate и повторную проверку состояния непосредственно перед promote.
- Выполнить ready/promote в предусмотренном blue-green workflow.
- Обновить DNS только после подтверждения трафика по IP. Если используются профили подписки без смены общего DNS, проверить выдачу обоих профилей и порядок предпочтения.
- Перевести тестовых пользователей, затем основной трафик контролируемым этапом.
- Сохранить старый узел и его конфигурацию на всё окно наблюдения.
- Проверять heartbeat, долю успешных подключений, ошибки авторизации, latency, throughput, доступность API/подписок и системные логи.
- При регрессии вернуть DNS/предпочтение/профиль на старый узел и подтвердить восстановление трафика.

**Выход:** основной трафик обслуживается новым Secondary; rollback на старый узел проверен или практически доступен.

### P0.6. Вывод старого сервера

Разрешён только после выполнения всех условий:

- новый узел прошёл клиентский smoke и окно наблюдения;
- подписки и DNS указывают на корректные endpoints;
- backup старого состояния проверен;
- rollback больше не требуется в рамках срока отключения;
- старый peer корректно удаляется из подписок и service plane по штатной последовательности.

Не удалять старый Secondary до завершения переключения. Удаление VPN device и удаление service-plane peer — разные операции; выполнять их в правильном порядке по runbook.

### P0 acceptance criteria

- [ ] Новый Secondary развёрнут с уникальными AgentID/PeerID/material/slot.
- [ ] Старый узел не повреждён и сохраняет возможность rollback до конца миграции.
- [ ] Новый узел принимает реальные внешние VLESS-подключения.
- [ ] Подписка содержит рабочий профиль нового узла.
- [ ] Основной трафик переключён на новый узел.
- [ ] Проверены основные сервисы и мониторинг после переключения.
- [ ] Зафиксированы результаты, время переключения и rollback-инструкция.
- [ ] Старый сервер выведен только после приёмки нового.

## 3. P1 — целевая региональная HA-архитектура

### 3.1. Модель размещения и именования

Отказаться от использования primary/secondary как постоянного обозначения географии. Это роли в текущей реализации, а не региональная принадлежность.

Целевая модель:

- регион RU;
- регион INTL;
- у каждого узла стабильная географическая/функциональная идентичность;
- роли active/standby или active/active задаются отдельно и могут меняться без переименования узла.

Пример будущих идентификаторов: ru-edge-1, ru-edge-2, intl-edge-1, intl-edge-2. Это ориентир для новой модели, а не требование немедленно иметь четыре сервера.

### 3.2. Режим работы

Принять гибридный режим:

- каждый регион способен самостоятельно обслуживать свой Data Plane;
- критичные сервисы имеют межрегиональный резерв;
- отказ одного узла не должен останавливать регион;
- отказ целого региона не должен полностью останавливать платформу;
- дополнительные сервисы (например, lampck и прочие необязательные компоненты) не обязаны зеркалироваться.

### 3.3. Разделение Control Plane и Data Plane

**Data Plane:** VLESS/Reality, WireGuard и другие транспортные компоненты, локальные runtime-конфигурации и маршрутизация пользовательского трафика.

Требование: уже настроенный Data Plane продолжает обслуживать подключения по последней валидной конфигурации при недоступности Control Plane. Обработка каждого нового подключения не должна синхронно зависеть от единственного центрального API.

**Control Plane:** API управления, оркестрация узлов, регистрация и выдача конфигураций, подписки, управление пользователями и распространение изменений.

Требование: Control Plane не должен быть единственной точкой отказа. Нужно определить репликацию состояния, выбор лидера/источника истины, fencing и восстановление после потери узла.

### 3.4. Классы сервисов

| Класс | Сервисы | Требование |
|---|---|---|
| Critical | VLESS/Data Plane, туннели, выдача подписок, доступ пользователей и необходимая авторизация | Резервирование; локальная работа при потере Control Plane |
| Core | Основные API и сервисы, необходимые для штатной работы платформы | Резервирование и восстановление после отказа узла/региона |
| Optional | lampck и прочие дополнительные сервисы | Допускается региональная установка без зеркала |

Фактическую классификацию каждого сервиса подтвердить по коду и runtime-зависимостям. Не считать сервис optional только по названию.

### 3.5. Состояние и репликация

Для каждого типа состояния определить:

- источник истины;
- владельца записи;
- направление и задержку репликации;
- допустимый RPO/RTO;
- поведение при разделении сети;
- процедуру восстановления и rollback.

Отдельно рассмотреть: пользовательские данные, конфигурации узлов, подписки, ключи и сертификаты, peer material, runtime state, очереди/фоновые задания и DNS.

Секреты и сертификаты нельзя просто копировать без модели доверия. Нужны ротация, overlap-период, обновление доверенных CA и автоматическая миграция старых установок.

### 3.6. Split-brain и failover

- Определить единственный механизм принятия решений о записи/лидерстве.
- Исключить одновременное принятие конфликтующих изменений двумя изолированными узлами.
- Использовать lease/quorum/fencing или другой обоснованный механизм; простого heartbeat недостаточно.
- Разделить health checks Control Plane и пользовательского Data Plane.
- Failover должен иметь проверяемые условия, таймауты, hysteresis и безопасный failback.
- DNS — только один из механизмов переключения; он не переносит уже установленные TCP-сессии. Клиентские профили должны иметь несколько рабочих endpoint либо другой механизм переподключения.

## 4. План архитектурной работы

| Этап | Результат |
|---|---|
| A. Incident/dependency mapping | Карта причин, почему отказ Primary остановил сервисы; граф зависимостей сервисов и API |
| B. Service inventory | Реестр Critical/Core/Optional, владельцев состояния и требований доступности |
| C. HA design | Целевая топология RU/INTL, роли узлов, Control/Data Plane, RPO/RTO |
| D. State replication | Проект репликации конфигураций, пользовательских данных, секретов и runtime state |
| E. Failure semantics | Split-brain prevention, fencing, failover/failback, поведение при потере региона |
| F. Compatibility/migrations | Переход от primary/secondary к region/node identity с автоматической миграцией старых конфигураций |
| G. Implementation | Поэтапные изменения API, схемы данных, bootstrap, operator и runtime |
| H. Failure drills | Проверки отказа узла, Control Plane, межрегиональной связи и целого региона |

## 5. Обязательные требования к изменениям и миграциям

Каждая реализация должна учитывать:

1. Совместимость старых конфигураций и форматов; миграция должна быть автоматической и идемпотентной.
2. Смешанные версии на время обновления: старые и новые агенты/узлы должны иметь определённое совместимое поведение.
3. Ротацию сертификатов и ключей с периодом одновременного доверия старому и новому материалу, если это безопасно.
4. Прерывание миграции: безопасное продолжение или rollback после перезапуска.
5. Неизменность публичных API либо версионированный переход.
6. Отсутствие потери пользовательского трафика при обновлении Control Plane.
7. Явный fail-closed при неоднозначном или конфликтном состоянии.
8. Наличие ручного recovery-пути, не требующего доступа к отказавшему узлу.

## 6. Порядок исполнения и ограничения

1. Сначала завершить P0 — второй Secondary и перевод трафика.
2. Не блокировать P0 полной переработкой Control Plane или переименованием сущностей.
3. Не выполнять destructive cleanup старого узла до завершения наблюдения.
4. Не запускать CI/Actions автоматически: тесты запускаются вручную по отдельному решению.
5. Не выполнять production deploy, DNS cutover или удаление узлов без отдельной команды на конкретную операцию.
6. После P0 начать с incident/dependency mapping, а не с преждевременного внедрения репликации.
7. Все изменения архитектуры фиксировать в этом плане и связанных runbook; обновлять английскую документацию при изменении контрактов.

## 7. Ближайшие действия

- [ ] Получить от оператора IP/hostname нового Secondary, регион, ОС и срок отключения старого сервера.
- [ ] Проверить текущие inventory, peer slots, версии и свободный slot.
- [ ] Сопоставить фактическое состояние с docs/ru/SECONDARY-DEPLOY.md и docs/ru/BLUE-GREEN-SECONDARY.md.
- [ ] Провести preflight нового сервера.
- [ ] Выполнить deploy без promote.
- [ ] Пройти внешний клиентский smoke.
- [ ] Переключить трафик и выдержать окно наблюдения.
- [ ] Только после этого завершить вывод старого узла.
- [ ] Затем выполнить этап A архитектурного плана.

**Блокирующие входные данные для P0:** адрес нового сервера (IP/hostname), регион и ОС; доступ/SSH-ключ и подтверждённый fingerprint; точный срок отключения текущего узла. Секреты и пароли в репозиторий не передавать.
